Seven defects, none of them visible in a dashboard

Every one is a mistake an analytics team actually ships. Not one of them has a bad column, a failed schema test, or an anomalous time series.

DefectCaught byWhy nothing else sees it
Region lookup table never got the newest regionCON-01Every row is valid. The join is inner, so 10% of revenue silently leaves the slice
An integration creates accounts with no segmentCON-02Nulls are legal. The slice just quietly omits 5% of the money
order_items is at line-item grain, not order grainCON-04The join works. It just multiplies rows, inflating revenue 150% — consistently, so no monitor ever alerts
A promo batch file was loaded twiceIDN-01Both loads are valid rows. Only comparing metrics against each other reveals it
active_users counts distinct users but is declared additiveIDN-03Nothing is wrong with the data or the SQL. The metric is labelled wrong, and every consumer summing a daily series over-counts fifteenfold
The ticket pipeline stopped 40 hours agoTMP-01The data is internally perfect. It is simply old
A late CRM sync rewrote a closed monthTMP-03Nothing is wrong now. What changed is the past

IDN-03 is the one worth pausing on. A metric computed daily and rolled up must equal the same metric computed natively at month. When it does not, the definition is lying about itself — and no schema test, freshness monitor, or dbt test is looking at that.

Why this isn't a tool you already have

Not dbt tests

Column-level assertions are dbt's job and dbt does them well. But none of the seven defects above has a bad column. They live in the relationship between a definition and the data, which column tests never compute.

Not anomaly detection

Statistical monitors catch changes. They cannot catch wrongness. A metric wrong since the day it was written never moves — the 150% fan-out looks perfectly stable, forever.

Not a golden query suite

A hand-written suite rots at exactly the rate the definitions do. Assay generates its checks from the definitions, so a metric change regenerates its own checks and there is nothing to keep in sync.

Not a semantic layer

dbt, Cube and AtScale make a number consistent. The definition is the thing that might be wrong, and a layer whose job is to apply it faithfully cannot audit it.

Run it yourself in a minute

No warehouse, no credentials, no account. It runs against a local DuckDB file and prints the report above on your machine.

uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -e ".[dev]"

.venv/bin/python -m demo.seed demo/demo.duckdb
.venv/bin/python -m assay.run.cli \
  --contracts demo/contracts.yml --database demo/demo.duckdb

# then restate a closed month and run again —
# this is the finding at the top of this page
.venv/bin/python -m demo.seed demo/demo.duckdb --backfill
.venv/bin/python -m assay.run.cli \
  --contracts demo/contracts.yml --database demo/demo.duckdb

Exit code is 2 on a blocking failure, so it gates a CI job unchanged. Verified against DuckDB and a live Snowflake account — byte-identical reports, under a SELECT-only role.

The model resolves intent into a typed plan. It never writes SQL, never reaches the warehouse, and never decides whether an answer is correct — a deterministic gate does that, and it wins when the two disagree.
